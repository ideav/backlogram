# Замер: иерархический OLTP на квартетах (issue #569)

Дата: 2026-09-10. Окружение: Windows 11, 12 логических ядер, 16 ГБ RAM, NVMe;
PostgreSQL 16.4 (портативный), `shared_buffers=2GB`, `work_mem=256MB`, `fsync=off`
(влияет только на загрузку, не на чтение). Без партиций.

## Выводы (кратко)

1. Правило частотности обязательно: hier8 при 1,1 зап./группу хуже плоского и по строкам (+1%), и по байтам (+3%).
2. Агрегаты по размерностям разреза — кратный выигрыш (счёт по филиалам 53× на hier2; по типам 2,9× на hier4).
3. Меры нижнего уровня иерархия замедляет (Q1 3,5×; Q3 1,4×) — лечится накопителями на разрезе (3–6× быстрее плоского), ценой инкремента на вставку.
4. Точечный OLTP-доступ одинаков во всех квартетных раскладках.
5. Широкая таблица остаётся на порядок компактнее и быстрее простых агрегатов — иерархия сокращает разрыв, не отменяя его.

Оговорки: один корпус, одна машина, синтетика с независимыми полями (реальные корреляции
уменьшают число групп → выигрыш растёт), без партиций, 100 вопросов масштаба нет —
абсолютные числа на 703 млн будут другими, проверять там.

### Стенд повторного прогона (13.09.2026)

WSL2 Ubuntu на Windows 11, хост 12 логических ядер, виртуалке отдано 6 ГБ RAM, NVMe.
PostgreSQL **16.15** портативной сборкой (в исходном прогоне — 16.4), те же
`shared_buffers=2GB`, `work_mem=256MB`, `fsync=off`. Загружены `wide`, `flat`, `hier4`, `jb`
(`hier2`/`hier8` не нужны ни одному запросу `bench4.sql`, в `gen.py` оставлен только `hier4`;
на содержимое остальных раскладок это не влияет — рандом расходуется в `tx_fields()`,
а раскладки его не трогают).

**Корпус воспроизвёлся точно:** `flat` 45 999 540 строк, `hier4` 42 511 695, групп 102 423,
9,8 транзакции на группу. Размеры совпали до мегабайта с исходным прогоном: `wide`
390/67/**458 МБ**, `flat` 2814/3081/**5896 МБ**, `hier4` 2602/2883/**5486 МБ**; `jb` 1687 МБ
против 1676 МБ (расхождение 0,7%, GIN строится недетерминированно по размеру).
Времена загрузки: `wide`+`flat`+`hier4` — 3 мин 54 с, `jb` с двумя индексами — 1 мин 31 с.

Из-за 6 ГБ памяти против 16 абсолютные времена с прежними таблицами сравнивать нельзя,
поэтому ниже только сопоставления внутри одного прогона. Все числа — второй, тёплый прогон.

### S1. Поиск по реквизиту, под который не заведён свой индекс

`RRN` не входит ни в один индекс `wide` (там `PK(id)`, `(DT,Gosb)`, `(pan)`).

| раскладка | план | время | буферов |
|---|---|---:|---:|
| `wide` | Parallel Seq Scan | **131,4 мс** | 49 936 |
| `flat` | Index Scan `(t, lower(left(val,127)))` | **0,064 мс** | 5 |
| `hier4` | Index Scan, тот же индекс | **0,043 мс** | 5 |
| `jb` | Bitmap Index Scan `jb_gin` | **0,062 мс** | 5 |

Квартеты быстрее широкой таблицы в **2000–3000 раз** при в 10 000 раз меньшем вводе-выводе,
причём `wide` при этом целиком в кеше (`shared hit`, ни одного `read`) — это её лучший случай.
**jsonb с GIN идёт вровень с квартетами** (0,062 против 0,064 мс): на этой оси честный
расклад — «квартеты и jsonb против широкой таблицы», а не «квартеты против всех».

### S2. Связь: обход по ребру против сборки группы по значениям

«Все транзакции той же группы, что транзакция с этим PAN, и сумма их `amount`» (18 соседей).

| раскладка | как | время |
|---|---|---:|
| `hier4` | один запрос по рёбрам `up` | **0,317 мс** |
| `wide` | сравнение четырёх колонок | **0,347 мс** |
| `jb` | два round-trip'а: документ, затем соседи | **0,321 + 1,006 = 1,33 мс** |

**Отрицательный результат, ожидавшийся заранее:** ребро не даёт выигрыша над сравнением
значений — 0,317 против 0,347 мс это шум. Причина в корпусе: в банковской транзакции связь
вырождена, группа выводится из четырёх полей, поэтому «ребро» любой схеме восстанавливается
предикатом. Преимущество графа надо мерить там, где связь произвольная и из данных не выводится.
jsonb здесь вчетверо медленнее — ему нужны два обращения вместо одного.

### S3. Новый 55-й реквизит на миллион уже лежащих записей

| раскладка | операция | время | размер до → после | прирост |
|---|---|---:|---:|---:|
| `wide` | `ALTER` 2 мс + `UPDATE` всех строк | **19,4 с** | 458 → 917 МБ | **+459 МБ (×2,0)** |
| `jb` | `UPDATE doc \|\| ...` всех документов | **103,1 с** | 1687 → 3049 МБ | **+1362 МБ (×1,8)** |
| `flat` | `INSERT` миллиона квартетов `t=1054` | 45,9 с | 5896 → 5982 МБ | **+86 МБ (+1,5%)** |
| `hier4` | то же | 48,0 с | 5486 → 5572 МБ | **+86 МБ (+1,6%)** |

`VACUUM ANALYZE` после: `wide` 1,7 с, `jb` 22,4 с, `flat` 1,7 с, `hier4` 1,2 с — и **размеры
не изменились ни на мегабайт**: обычный `VACUUM` место операционной системе не возвращает,
для этого нужен `VACUUM FULL` с эксклюзивной блокировкой таблицы.

Это единственная из трёх осей, где расклад переворачивается, и переворачивается он по хранению,
а не по времени: у квартетов новый реквизит — это вставка миллиона строк, у широкой таблицы и
jsonb — перезапись миллиона существующих со всеми последствиями MVCC. По времени быстрее всех
оказалась широкая таблица (19,4 с), jsonb медленнее квартетов вдвое.

### Что из этого следует

Плата за универсальность (индекс в 3081 МБ) отбивается ровно на двух вещах: поиске по
произвольному реквизиту и дешёвом расширении схемы. На банковском корпусе не отбивается
третья, заявленная в статье, — связи; и честно показать её на этих данных нельзя.
