# Issue 624: замкнутый контур — подтверждение email → сборка → письмо с результатом

До этой задачи контур был разомкнут: форма регистрировала заявку, сборку
запускали руками кнопкой в @Integrammbot, результат отправляли руками. Теперь
заявка с email проходит весь путь сама, и первым шагом стоит **подтверждение
адреса (double opt-in)**: пока клиент не перешёл по ссылке из письма, не
создаётся ни issue, ни уведомления, и сборка не начинается.

Почему подтверждение именно в начале, а не в конце: сборку делает ИИ-агент, и
каждая заявка стоит денег. Форма без подтверждения — это оплаченная сборка на
каждую опечатку в адресе и на каждую заявку, отправленную «за кого-то».

## Поток

```
        форма ideav.ru (source=excel-to-app | excel-constructor)
                     │
                     ▼
        excel-to-app.php ── контакт не email? ──► публикация сразу (как до #624)
                     │                            issue + Telegram, запуск руками
          контакт = email
                     ▼
     очередь: <queue>/<id>/ (request.json + files/)     статус pending_confirmation
                     │
                     ▼
        письмо-подтверждение на адрес клиента (TTL 24 ч)
                     │
                     ▼  клиент перешёл по ссылке
        excel-to-app-confirm.php                        статус confirmed
                     ├─► вложения → GitHub, issue, уведомление оператору
                     └─► страница «Заявка подтверждена — приступаем»
                     │
                     ▼  сборщик забирает работу сам (POST action=claim)
        excel-to-app-build.php                          статус building
                     │
                     ▼  сборщик отчитался (POST action=deliver)
        письмо «приложение готово» клиенту               статус delivered
```

Не подтвердил в течение TTL → `excel-to-app-queue.php` (cron) удаляет заявку
вместе с файлами. Ровно это обещано клиенту в письме.

## Решения владельца (issue #624, комментарий от 29.09.2026)

| Вопрос | Решение |
|---|---|
| Заявки с Telegram-контактом | оставляем как сейчас — публикуются сразу, запуск руками |
| Где хранить очередь и статусы | файлы рядом с интейком |
| Кто ставит задачу в bridge | на усмотрение исполнителя — сделана очередь, из которой сборщик забирает работу сам |
| TTL ссылки подтверждения | 24 часа |
| Текст писем | без ограничений |

### Почему мост сделан как pull, а не вызовом сборщика из PHP

- Веб-хост не достаёт до машины сборщика — и не должен: это значило бы держать
  во фронтовом PHP доступ в контур сборки.
- Pull переживает перезапуски и обновления бота: работа лежит в очереди и
  дождётся, а не теряется в неудавшемся исходящем запросе.
- `claim`/`deliver` делают шаг идемпотентным: заявка уходит в сборку один раз,
  повторный `claim` её уже не видит, повторный `deliver` не рассылает второе
  письмо.

## Формат заявки в очереди

Каталог `<queue>/<id>/`, где `<id>` — `YYYYMMDD-HHMMSS-xxxxxxxx` (он же каталог
вложений в репозитории: `orders/<id>/`).

```
<queue>/20260929-210000-1a2b3c4d/
├── request.json      статус, поля заявки, хеш токена, история переходов
└── files/
    └── 01-orders.csv
```

`request.json` хранит **sha256-хеш** секрета из токена, не сам секрет: чтения
каталога очереди недостаточно, чтобы подтвердить чужую заявку. Одноразовость
ссылки держит статус (второй раз `pending_confirmation` не встретится), а
сохранённый хеш позволяет отличить повторный клик по своей ссылке от чужого
мусорного токена и показать «уже подтверждено» вместо «не найдено».

Переход `pending_confirmation → confirmed` делается под `flock`: по ссылке из
письма прилетает не одно обращение (двойной клик, префетч почтового клиента), а
сборка должна стартовать один раз.

## Протокол моста

`POST /excel-to-app-build.php`, заголовок `X-Build-Token: <INTAKE_BUILD_TOKEN>`
(или `Authorization: Bearer` — где он доходит, см. ниже). Поля — форма или
JSON-тело. Токен не задан → `503` и эндпоинт ничего не делает: открытым он
не бывает.

| Действие | Поля | Что делает |
| --- | --- | --- |
| `claim` | `limit` (1–20, по умолчанию 5) | Отдаёт подтверждённые заявки и переводит их в `building`. В ответе: `id`, контакт, тематика, `issue_url`, `issue_number`, `attachments[]`. |
| `deliver` | `request_id`, `app_url`, `admin_login`, `admin_password`, `what_inside`, `topic`/`topic_short`, `price_razbor`, `dev_range` | Отправляет клиенту письмо «приложение готово», статус → `delivered`. Повтор — `{"ok":true,"already":true}` без второго письма. Письмо не ушло — `502`, статус не меняется: запрос можно повторить. |
| `fail` | `request_id`, `reason` | Статус → `failed` + сигнал оператору в Telegram. |
| `status` | `request_id` | Текущее состояние заявки (без хеша токена). |

**На нашем хостинге работает только `X-Build-Token`.** Apache отдаёт PHP как
CGI, а заголовок `Authorization` в CGI не передаётся без `CGIPassAuth On` —
запрос с `Bearer` получает честный `401`. Проверено на обоих доменах при
выкатке 03.10.2026; поэтому в примерах ниже заголовок именно такой.

Пример:

```bash
curl -sS -X POST https://ideav.ru/excel-to-app-build.php \
  -H 'X-Build-Token: ***' -H 'Content-Type: application/json' \
  -d '{"action":"claim","limit":3}'

curl -sS -X POST https://ideav.ru/excel-to-app-build.php \
  -H 'X-Build-Token: ***' -H 'Content-Type: application/json' \
  -d '{"action":"deliver","request_id":"20260929-210000-1a2b3c4d",
       "app_url":"https://ideav.ru/nteaclub/","admin_login":"nteaclub",
       "admin_password":"NteaAdmin2026","topic_short":"интернет-магазина",
       "what_inside":"— Каталог: 198 товаров из вашего прайса…"}'
```

## Конфигурация

Всё читается окружением-в-первую-очередь (`intake_config()`), пример —
`public/telegram-config.example.php`.

| Имя | По умолчанию | Назначение |
| --- | --- | --- |
| `INTAKE_CONFIRM_REQUIRED` | `1` | Выключатель double opt-in. `0` — поведение как до #624. |
| `INTAKE_CONFIRM_SOURCES` | `excel-to-app,excel-constructor` | Формы, за которыми стоит автоматическая сборка. Остальные (`catalog-matching`, `uc-*`) — обращения к оператору, подтверждение там только теряет лид. |
| `INTAKE_CONFIRM_TTL` | `86400` | Срок жизни ссылки, сек. Решение владельца — 24 ч. |
| `INTAKE_CONFIRM_MAX_PER_EMAIL` | `3` | Заявок на один адрес за сутки (IP-лимит не мешает засыпать чужой адрес с разных адресов сети). |
| `INTAKE_CONFIRM_URL` | по текущему хосту | База ссылки подтверждения. |
| `INTAKE_QUEUE_DIR` | `<родитель вебрута>/excel-to-app-queue` | Каталог очереди. **Вне вебрута:** внутри лежат файлы клиентов. |
| `INTAKE_QUEUE_KEEP_DELIVERED` | `2592000` | Сколько держать доставленные заявки, сек. |
| `INTAKE_MAIL_FROM` | `welcome@ideav.ru` | Отправитель. Только домен с SPF/DKIM/DMARC. |
| `INTAKE_MAIL_FROM_NAME` | `Интеграм` | Отображаемое имя (MIME-кодируется). |
| `INTAKE_MAIL_REPLY_TO` | `abc@integram.io` | Адрес для ответа. |
| `INTAKE_MAIL_BCC` | — | Копия себе, контроль отправки. |
| `INTAKE_MAIL_TRANSPORT` | `mail` | `mail` или `file` — сухой прогон без отправки. |
| `INTAKE_MAIL_FILE` | — | Куда писать письма при `transport=file`. |
| `INTAKE_BUILD_TOKEN` | — | Токен моста. Только в окружении. Не задан → мост отвечает `503`. |

## Cron

```
*/10 * * * * php /path/to/webroot/excel-to-app-queue.php
```

Скрипт удаляет неподтверждённые заявки с истёкшим TTL (вместе с файлами) и
добирает публикацию подтверждённых заявок, у которых она не удалась: GitHub и
Telegram с этого хоста отваливаются регулярно (ровно из-за этого у лендинга
excel-to-app.ru есть `order-deliver.php`), а подтверждённую заявку терять
нельзя. Только CLI: через веб отвечает 404.

## Что происходит, когда что-то не работает

| Сбой | Поведение |
| --- | --- |
| Почта хоста легла (письмо-подтверждение не ушло) | Заявка не теряется: убирается из очереди и публикуется сразу, как до #624 — оператор увидит её в Telegram. В лог пишется причина. |
| Очередь недоступна (нет прав/места) | То же: публикация напрямую. |
| GitHub/Telegram упали при подтверждении | Подтверждение остаётся в силе (иначе ссылка из письма перестанет работать), заявка помечается `publish_error`, публикацию добирает cron. |
| Письмо с результатом не ушло | `deliver` отвечает `502`, статус не двигается — сборщик повторит запрос. «Доставленной» заявка молча не станет. |

## Выкатка

Мерж в main ничего не публикует — заливка руками (см.
[`docs/issue-304-excel-to-app-backend.md`](issue-304-excel-to-app-backend.md)).
Порядок для ideav.ru:

1. Залить в вебрут: `intake-mail.php`, `intake-queue.php`, `intake-publish.php`,
   `excel-to-app.php`, `excel-to-app-confirm.php`, `excel-to-app-build.php`,
   `excel-to-app-queue.php`.
2. Создать каталог очереди **вне вебрута**, владелец — пользователь PHP, права
   `0700`; прописать `INTAKE_QUEUE_DIR`.
3. Задать `INTAKE_BUILD_TOKEN` (длинная случайная строка) в окружении PHP-FPM;
   тот же токен — сборщику.
4. Проверить почту сухим прогоном: `INTAKE_MAIL_TRANSPORT=file` +
   `INTAKE_MAIL_FILE=/tmp/intake-mail.log`, отправить заявку, посмотреть тему и
   заголовки; затем вернуть `mail`.
5. Отправить настоящую заявку на свой адрес и пройти весь путь: письмо → ссылка
   → issue → `claim` → `deliver` → письмо с результатом.
6. Поставить cron из раздела выше.

Проверка кодами после заливки: `POST /excel-to-app.php` без полей → `400`
(**с заголовком `Referer` своего домена**: без него раньше срабатывает
проверка источника и ответ будет `403`),
`GET /excel-to-app-confirm.php` без токена → `400`,
`GET /excel-to-app-build.php` → `405`, `POST` без токена → `401`,
`GET /excel-to-app-queue.php` → `404`.

### Как контур разложен на 92.242.60.37 (выкачен 03.10.2026)

| Что | Где |
| --- | --- |
| Очередь ideav.ru | `/var/www/www-root/data/intake-queues/excel-to-app` (`INTAKE_QUEUE_DIR`) |
| Очередь лендинга | `/var/www/www-root/data/intake-queues/excel-order` (`ORDER_QUEUE_DIR`) |
| Настройки ideav.ru | `ideav.ru/telegram-config.php` (0600, владелец `www-root`) |
| Настройки лендинга | `excel-to-app.ru/order-config.php` (0600) |
| Токены моста | `/root/.intake-build-token`, `/root/.order-build-token` (0600) — их же отдать сборщику |
| Cron | `*/10` → `ideav.ru/excel-to-app-queue.php`, `*/5` → `excel-to-app.ru/order-deliver.php` |

Каталоги очередей лежат не «рядом с вебрутом по умолчанию», а в отдельном
`intake-queues/`: в `/var/www/www-root/data/www` сложены вебруты всех сайтов
сервера, и однажды заведённый там vhost сделал бы файлы клиентов публичными.

Грабля окружения: у Apache на этом сервере `PrivateTmp=yes`, поэтому
`sys_get_temp_dir()` в PHP — это `/tmp/systemd-private-*-apache2.service-*/tmp`,
а не тот `/tmp`, который видно по ssh. Там лежат счётчики лимитов из
`order.php` и всё, что пишется в `/tmp` из веба: искать логи надо именно в
приватном каталоге.

## Тот же контур на лендинге excel-to-app.ru

Форма лендинга шлёт заявки не в `public/excel-to-app.php`, а в собственный
эндпоинт `site-excel/public/order.php` (спул + Telegram, см.
`site-excel/public/order-lib.php`): отдельный домен, отдельный вебрут. Контур
подтверждения там **тот же самый** — расхождение двух реализаций double opt-in
означало бы разный срок ссылки, разные письма и разный токен на двух доменах,
где человек видит одно и то же предложение.

Поэтому источник библиотеки один (`public/intake-*.php`), а в вебруте лендинга
лежат **сгенерированные копии**:

```
node scripts/sync-excel-intake.mjs
```

Копируются `intake-mail.php`, `intake-queue.php`, `intake-confirm-page.php`,
`intake-build.php` — у каждой копии в шапке написано, что править её нельзя.
Расхождение копии с источником ловит `tests/excel-landing-confirm.test.mjs`. Из
`intake-shared.php` библиотеке нужен только `intake_config()`, и на лендинге его
объявляет `order-intake.php` поверх `order_config()` — сам `intake-shared.php`
туда не переезжает.

### Что меняется и что нет

| Заявка | Поведение |
| --- | --- |
| `kind=demo`, контакт — email | очередь + письмо со ссылкой; оператор и сборщик видят её только после перехода |
| `kind=demo`, контакт — телеграм/телефон | как до #624: спул → Telegram сразу |
| `kind=razbor`, `kind=express` | как до #624: за ними нет автоматической сборки, лишний шаг только теряет лид |

Письма на обоих доменах уходят от `welcome@ideav.ru`: у `excel-to-app.ru` нет ни
SPF, ни DMARC, а оба сайта стоят на одном сервере (92.242.60.37), который в SPF
`ideav.ru` перечислен, — письмо от имени лендинга просто не дошло бы.

### Файлы лендинга

| Файл | Назначение |
| --- | --- |
| `site-excel/public/order-intake.php` | Связка: `intake_config()` поверх `order_config()`, каталог очереди, ссылка подтверждения, лимит на адрес, постановка заявки в очередь и её публикация оператору после подтверждения. |
| `site-excel/public/order-confirm.php` | Переход по ссылке из письма → спул оператору → страница из общей библиотеки. |
| `site-excel/public/order-build.php` | Мост к сборщику (`ORDER_BUILD_TOKEN`), вид заявки для сборщика, сигнал об ошибке тем же ботом. |
| `site-excel/public/order.php` | Один блок: `order_confirm_needed()` → `order_confirm_start()`. Остальное не менялось. |
| `site-excel/public/order-deliver.php` | Тот же cron: плюс уборка просроченных заявок и повторная отправка подтверждённых, не дошедших до оператора. |
| `site-excel/src/Landing.tsx` | Ответ `pending_confirmation` → экран «Подтвердите адрес» вместо «Вернёмся со ссылкой…». |

Цель Метрики (`GOALS.lead`) по-прежнему срабатывает в момент отправки формы, а
не подтверждения: это «человек оставил заявку», и переносить её на
подтверждение — отдельное решение по рекламе, а не часть этой задачи.

### Отличие от ideav.ru: файлы клиента

На ideav.ru вложения после подтверждения уезжают в GitHub, и сборщик получает
в `claim` ссылки на них. На лендинге GitHub нет: таблицы приходят оператору в
Telegram, как и раньше, а в заявке для сборщика остаются только имена файлов
(`files[]`, `files_via: telegram`) — чтобы было видно, что искать в чате.

| Имя | По умолчанию | Назначение |

| `INTAKE_SITE_URL` | `https://excel-to-app.ru` | Домен в подписи страницы. |

### Выкатка лендинга

Фронт собирается `npm run build:excel` (переменные — в
[`site-excel/README.md`](../site-excel/README.md)), PHP кладётся в вебрут
домена руками.

1. `node scripts/sync-excel-intake.mjs` — убедиться, что копии свежие.
2. Залить в вебрут: `order-intake.php`, `order-confirm.php`, `order-build.php`,
   `order-deliver.php`, `intake-mail.php`, `intake-queue.php`,
   `intake-confirm-page.php`, `intake-build.php`.
3. **`order.php` из репозитория не заливать целиком.** Прод опережает git
   (правки под #596 лежат поверх репозитория), и заливка затёрла бы их. Внести
   руками один блок «Подтверждение адреса (issue #624)» — он идёт сразу после
   сборки `$body` и до раздела «Очередь + доставка», и больше в файле ничего не
   меняется. `order-config.php` с токенами — только на сервере.
4. Создать каталог очереди вне вебрута, владелец — пользователь PHP, права
   `0700`; прописать `ORDER_QUEUE_DIR`.
5. Задать `ORDER_BUILD_TOKEN`; тот же токен — сборщику.
6. Сухой прогон почты (`INTAKE_MAIL_TRANSPORT=file`), затем настоящая заявка на
   свой адрес: письмо → ссылка → заявка в Telegram → `claim` → `deliver` →
   письмо с результатом.

Проверка кодами: `GET /order-confirm.php` без токена → `400`,
`GET /order-build.php` → `405`, `POST /order-build.php` без токена → `401`,
`GET /order-deliver.php` → `404`.
