## Аннотация

Три месяца память в нашей агентской обвязке была «включена». Потом появилась
телеметрия экспозиции — и выяснилось, что всё это время инъекция была пустой, и
никто этого не заметил. С этого начинается доклад, потому что это главный урок:
без замера экспозиции любые «до/после» бессмысленны — вы не знаете, был ли вообще
«после».

Стандартный способ дать агенту память — файл `AGENTS.md`/`CLAUDE.md`, который
целиком уезжает в контекст на каждом ходу и требования из которого идут с
наивысшим приоритетом. Такой файл только растёт, устаревает при каждом
перемещении файла в проекте и постепенно превращается в свалку, конкурирующую за
внимание модели.

Мы заменили его retrieval-слоем на хуках агентской обвязки: постоянная часть —
несколько строк, остальное подмешивается по релевантности к конкретному
запросу — выстраданные уроки, причинная цепь «симптом → причина → фикс» и куски
тикетов, причём ссылка или номер в запросе разворачивается в текст тикета до
поиска.

Дальше — две вещи, которые обычно не показывают. Первая: замер. Память запущена
как рандомизированный A/B, контрольные сессии не получают ни блоков, ни даже
уведомления о том, что память существует; экспозиция и латентность пишутся в
лог. Вторая: граница применимости. Память — подсказка, она не исполняет.
Повторяющаяся ошибка лечится не записью в память, а детерминированным
PreToolUse-хуком, который проверяет живое состояние мира и запрещает вызов.

Отдельно разберём память как поверхность атаки: текст чужого issue приезжает в
контекст агента на каждом ходу — это канал промпт-инъекции, а не просто контекст.

## Что показываю на сцене

- код хуков (recall, remember, guard) — компактный, читается со слайда;
- схему подмешивания и бюджет контекста;
- строки лога экспозиции с латентностью и таймаутами;
- цифры A/B: экспозиция, эффект, доверительные границы;
- три ошибки: таймаут retrieval на критическом пути, память вместо запрета,
  попытка сказать контрольной группе о памяти.

## Фактура, на которую опирается доклад

Проверено по коду и логам на 2026-08-02:

- Четыре хука в `~/.claude/settings.json`: `SessionStart`, `UserPromptSubmit`
  (recall), `Stop` (remember), `PreToolUse` на Bash (guard).
- Корпус поднят локально, привязка к репозиторию резолвится от `cwd` (`repo.sh`).
- Подмешиваются три типа блоков: закреплённые уроки, причинная цепь
  «симптом → причина → фикс», семантически релевантные тикеты.
- Ссылки и номера тикетов в запросе разворачиваются в текст тикета до поиска,
  свежий тикет дотягивается из GitHub.
- A/B: рандомизация по `session_id`, сплит 0.5; контрольная сессия не получает
  ничего, включая строку «память активна» (иначе агент ведёт себя иначе).
- `exposure.jsonl` — на 02.08.2026 160 записей за 8 дней (30 сессий): `ts`,
  `session`, `cwd`, `branch`, `regime`, `arm`, `blocks{pinned,causal,semantic}`,
  `latency_ms`, `bytes`, `err`.

| Показатель | Значение |
|---|---|
| Записей / сессий / дней | 160 / 30 / 8 |
| Темп | ≈ 20 ходов и 3,75 сессии в день |
| Ходов на сессию | медиана 4, максимум 23 |
| Сессии по плечам | on 21, off 9 |
| Сессии по репозиториям | crm 19, backlogram 7, прочие 4 |

| Латентность recall | p50 1 652 мс, p90 6 028 мс, p95 6 737 мс, max 8 136 мс |
| Таймауты | 3 из 128 ходов с памятью (2,3 %) |
| Блоки на ход (среднее) | pinned 4,0; causal 38,3; semantic 9,4 |
| Ходов без единого закреплённого урока | 81 из 160 |

Два вывода из среза:

1. **Латентность — уже готовый результат доклада.** Recall стоит на критическом
   пути каждого хода, и p90 в 6 секунд — это шесть секунд ожидания перед каждым
   ответом агента. Плюс 2,3 % таймаутов. Это самостоятельный слайд и живая
   инженерная задача, цифры для неё есть уже сейчас.
2. **Половина замера утекает.** Рандомизация включена только на crm; сессии в
   backlogram и остальных репозиториях всегда получают память и в сравнение не
   попадают — это 11 сессий из 30, треть трафика мимо эксперимента.
- Жёсткий запрет: `no-writes-to-closed-pr.py` — перед `git push` /
  `gh pr comment` живым вызовом `gh pr view` проверяет состояние PR и запрещает
  запись в `MERGED`/`CLOSED`. Fail-open при отсутствии сети или gh; аварийный
  обход маркером `# allow-closed-pr` в команде.
- Кейс, породивший запрет: коммиты по одной задаче ушли в ветку уже смерженного
  PR и не попали в main, пришлось переделывать отдельным PR. Сначала это
  записали в память как подсказку — ошибка повторилась; помог только хук.

## Замер: что уже спроектировано и посчитано

Дизайн замера описан в `packages/vecmory/docs/effect-measurement.md` (репозиторий
`ideav/python2node`) и заметно строже, чем «включили и посмотрели». Его и надо
рассказывать — это и есть содержательная часть доклада.

**Четыре слоя доказательства.** A — память доезжает (лог экспозиции). B — достаёт
нужное (офлайн-бенчмарк на золотых парах). C — меняет поведение (поведенческий
A/B на фиксированном наборе задач). D — снижает брак в живой работе. Ошибка
«мерить сразу D» и есть причина, по которой такие проекты не доказывают ничего.

**Арбитр слоя D — доля PR, на которые прилетел тикет-жалоба.** База посчитана по
2000 issues и 2000 PR: **21,6 %** свежих PR получают жалобу, поток — 107 PR в
неделю. Метрика извлекается механически, без судьи и разметки.

**Окно созревания замерено, а не назначено:** по 393 жалобам со ссылкой на
смерженный PR — 94 % приходят в первые 24 часа, 100 % в первые 7 суток, медиана
лага — полчаса. Отсюда окно 7 дней, а не месячный карантин.

**Календарь мощности** (α = 0,05, мощность 0,8, база 21,6 %, 53 PR/нед на арм):
эффект −30 % требует 535 PR на арм, то есть **3 октября 2026**. Доклад 15 октября
— финальный взгляд приходится на 12 дней раньше выступления.

**Три объявленных заранее взгляда с границей О'Брайена–Флеминга:** 22 августа
(p < 0,0005), 19 сентября (p < 0,0141), 3 октября (p < 0,0451). Остановка
возможна только на них. Цена права подглядывать посчитана симуляцией: при
еженедельных проверках и остановке на первом p < 0,05 ложная тревога срабатывает
в **20,6 %** случаев вместо 5.

**Мост «арм ↔ PR» пришлось переделывать по живому отказу.** Арм назначается на
сессию, исход живёт на PR. Первый ключ — ветка — врал: сессия идёт в главном
чекауте, а работа в `git worktree`, и в лог попадала ветка чекаута. При тридцати
воркtree это систематическая ошибка. Заменено на штамп `Vecmory-Session` в
коммите. На живых данных ветка не дала **ни одного** правильного ключа.

## Что было сделано в ходе подготовки заявки

Последний незакрытый пункт замера — команда `vecmory metrics`, считающая слой D
(PR ideav/python2node#198). Первый объявленный взгляд 22 августа, а срез,
посчитанный руками, каждый раз считается по-разному. Три правила зашиты в код:
окно созревания, только однозначный арм, вердикт только на объявленных датах.

Первый прогон на живых данных сразу дал материал для слайда: срез на 02.08
показывает **p = 0,047** и «−100 % к контролю» на n = 7 против n = 2 — ровно тот
мираж, который приносят на планёрку как доказательство. Команда его печатает и
вердикта не даёт.

Всплыли два числа, которые тоже идут в доклад:

- **Покрытие атрибуцией 63 %** (65 PR по штампу сессии, 4 по id claude.ai, 0 по
  ветке). Если удержится, к 3 октября выйдет ≈ 340 PR на арм вместо 535, и
  различимым останется эффект около −38 %, а не −30 %.
- **Баланс армов по PR — 50 против 19** при честном сплите 10/9 по сессиям. Долю
  брака это не портит (она нормирована на PR), но объяснение нужно до выводов:
  либо память меняет объём выпускаемых PR, либо в контроле что-то мешает
  доводить работу до PR.

## Отменённая рекомендация

Первая версия этого документа предлагала включить рандомизацию на `backlogram`,
чтобы «не терять треть сессий». **Это неверно и делать не нужно.** Решение
рандомизировать только `crm` принято осознанно и записано в `routes.tsv` и §5:
слой D существует только там, где есть поток PR и жалобы на них. В остальных
репозиториях измерять нечего, а половина сессий работала бы без памяти впустую —
это плата уроками без всякой отдачи.

Там же была ошибка в единице анализа: сессии и ходы вместо PR. Арбитр слоя D
считается на PR, и вся арифметика мощности уже сделана в §4 по правильной
единице.
